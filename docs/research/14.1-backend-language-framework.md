# §14.1 Backend language & framework — research report

**Research date:** 26 July 2026 (live web verification). Constraint applied: no Spring/Spring Boot; lightweight JVM (Kotlin-first) vs Go.

---

## 0. TL;DR

**Recommendation: Quarkus (Kotlin) first, Go (chi + sqlc/pgx) second.** The decisive facts: (a) the **Quarkus MCP server extension is the most mature MCP server implementation in the entire JVM ecosystem** — v1.13.0, streamable HTTP since early on ("first Java server SDK to support Streamable HTTP"), already supporting the 2026-07-28 stateless protocol; (b) Quarkus native image (20–50 MB RSS, 20–80 ms cold start) fully neutralizes the "JVM is too heavy for cheap PaaS" concern; (c) Quarkus has first-class, documented **OIDC multitenancy across distinct providers** (Entra/Google/Okta) — the only candidate where this is a config-level feature rather than hand-wiring. Go is a very close second with the **stable official Go MCP SDK (v1.6.1, Google collaboration)** and the best raw footprint, but costs you Kotlin proficiency and more hand-rolled security wiring. Ktor drops to third mainly because the **MCP Kotlin SDK is still pre-1.0 (0.13.0)** and its OpenAPI generation is experimental.

## 1. MCP Server SDK Maturity (July 2026) — the decisive criterion

| SDK | Latest | Status | Streamable HTTP | Embedding in a monolith |
|---|---|---|---|---|
| **Quarkus MCP Server** (quarkiverse, independent impl.) | **1.13.0** (June 2026) | Production-grade, tracks spec fast | Yes — legacy HTTP/SSE + Streamable HTTP in one artifact (`quarkus-mcp-server-http`); auto-detects stateless (2026-07-28) vs stateful clients on the same endpoint | Best-in-class: declarative `@Tool`/`@Resource`/`@Prompt` CDI beans that directly inject your service layer |
| **MCP Go SDK** (official, w/ Google) | **v1.6.1 stable**, v1.7.0-pre.3 (targets 2026-07-28 protocol) | Stable v1.x line, 4.9k stars, OpenSSF Scorecard, full-spec ambition | Yes — streamable HTTP transport with stateless option | `StreamableHTTPHandler` is a standard `http.Handler` → mounts on any chi/echo/net-http mux next to your REST routes |
| **MCP Java SDK** (official, Anthropic + Spring AI team) | **2.0.0** (June 2026), aligned to 2025-11-25 spec | Stable v2, 3.6k stars | Yes — SSE deprecated in favor of Streamable HTTP in the 2.0 cycle | Core works without Spring via **Jakarta Servlet transport** → embeds in Javalin/Jetty; awkward in non-servlet Ktor |
| **MCP Kotlin SDK** (official, w/ JetBrains) | **0.13.0** (June 2026) — **still pre-1.0** | Active (1.4k stars), good features (tasks, typed elicitation, DNS-rebinding protection by default) | Yes — stdio, Streamable HTTP (recommended), SSE, WebSocket; `mcpStreamableHttp()` Ktor route builders | Excellent *for Ktor specifically* — but pre-1.0 API churn risk on a day-one hard requirement |

Sources: [quarkus-mcp-server repo](https://github.com/quarkiverse/quarkus-mcp-server) · [Quarkus streamable-HTTP announcement](https://quarkus.io/blog/streamable-http-mcp/) · [transports doc](https://docs.quarkiverse.io/quarkus-mcp-server/dev/concepts-transports.html) · [go-sdk](https://github.com/modelcontextprotocol/go-sdk) + [releases](https://github.com/modelcontextprotocol/go-sdk/releases) · [java-sdk](https://github.com/modelcontextprotocol/java-sdk) + [releases](https://github.com/modelcontextprotocol/java-sdk/releases) · [kotlin-sdk](https://github.com/modelcontextprotocol/kotlin-sdk) + [releases](https://github.com/modelcontextprotocol/kotlin-sdk/releases)

**Read on this:** for a *day-one* embedded MCP module sharing the service layer, Quarkus and Go are the two low-risk paths. Ktor's path exists and is idiomatic but rides a 0.x SDK. Javalin could ride the stable Java SDK 2.0 via its servlet transport.

## 2. JVM Candidates (mid-2026 state)

### Quarkus — 3.33 LTS (July 2026; LTS supported to Mar 2027, Red Hat build available)
- **Health:** LTS cadence with 12-month critical/security patch windows; Red Hat commercial backing. Sources: [quarkus.io/releases](https://quarkus.io/releases/), [endoflife.date/quarkus-framework](https://endoflife.date/quarkus-framework), [Red Hat 3.33 LTS article](https://developers.redhat.com/articles/2026/07/03/red-hat-build-quarkus-3-33-lts-release).
- **Footprint:** native image 20–50 MB RSS, 20–80 ms cold start, runs on Cloud Run at `--memory 128Mi`; JVM mode 200–500 MB / 3–10 s cold start ([oneuptime Cloud Run guide, Feb 2026](https://oneuptime.com/blog/post/2026-02-17-quarkus-native-application-cloud-run-minimal-cold-start/view)). Native build cost: 5–10 min on beefy CI machines.
- **Security:** best-in-class here. `quarkus-oidc` **multitenancy explicitly supports distinct providers per tenant** (Keycloak, Google, Entra, Okta) via `TenantResolver` — [official guide](https://quarkus.io/guides/security-openid-connect-multitenancy). CSRF filter extension, declarative `@RolesAllowed`/`@PermissionsAllowed` (usable for row-level checks with custom permissions), curated platform BOM = one coordinated dependency tree (supply-chain plus), CVE handling backed by Red Hat.
- **PostgreSQL/ORM:** Hibernate ORM + Panache (Kotlin variant exists), or jOOQ/Exposed via extensions; **Flyway/Liquibase built-in extensions**.
- **OpenAPI:** SmallRye OpenAPI built-in — annotation/code-derived spec served at `/openapi`, feeds openapi-generator for TS client types.
- **Jobs:** built-in `@Scheduled` scheduler + Quartz extension; **JobRunr 8.6 officially supports Quarkus 3.33 LTS** ([JobRunr releases](https://github.com/jobrunr/jobrunr/releases)) for persistent/queued jobs (LLM extraction pipeline).
- **Kotlin:** officially supported ("first class"), `suspend` handlers in quarkus-rest ([guide](https://quarkus.io/guides/kotlin)) — but docs/examples are Java-first; expect to translate.
- **AI-assist:** very high — conventional annotations, enormous official guide corpus, Dev UI. One caveat: native-image reflection issues are the classic place AI agents flail; mitigate by staying JVM-mode in dev and testing native in CI.

### Ktor — 3.5.0 (June 2026)
- **Health:** strong JetBrains cadence — 3.4.0 (Jan 2026) added OpenAPI generation, structured-concurrency request lifecycle; 3.5.0 added RFC 7616 digest auth, typed config, session hardening. Sources: [3.4 blog](https://blog.jetbrains.com/kotlin/2026/01/ktor-3-4-0-is-now-available/), [3.5 notes](https://ktor.io/docs/whats-new-350.html), [releases](https://ktor.io/docs/releases.html).
- **Footprint:** JVM mode realistically ~150–300 MB RSS, 1–2 s start — fine on a 512 MB–1 GB always-on instance, not on 128–256 MB. GraalVM native supported but **CIO engine only** ([ktor.io/docs/graalvm.html](https://ktor.io/docs/graalvm.html)) and far less turnkey than Quarkus. CRaC is effectively a non-option on Cloud Run (no CRIU restore support in the platform; it's an AWS-Lambda-SnapStart-shaped technology).
- **Security:** OAuth/OIDC client plugin + JWT validation exist, but **multi-provider OIDC federation is hand-assembled**; authz is roll-your-own (or pac4j). CSRF plugin exists. Secure, but *defaults* are thinner — you build the security posture yourself.
- **ORM:** **Exposed 1.0 went stable Jan 2026** (stable API guarantee, R2DBC) — [JetBrains announcement](https://blog.jetbrains.com/kotlin/2026/01/exposed-1-0-is-now-available/); Flyway integrates fine.
- **OpenAPI:** new compiler-plugin-based generation in 3.4 is promising but **experimental (`@OptIn(ExperimentalKtorApi::class)`)** and infers from routing shape only — [docs](https://ktor.io/docs/openapi-spec-generation.html).
- **Jobs:** nothing built in; JobRunr (8.6, Kotlin-native support) or db-scheduler alongside.
- **AI-assist:** good — hugely represented in training corpora, but its DSL style means agents sometimes produce plausible-but-stale 2.x idioms.
- **MCP:** the natural home of the Kotlin SDK (`mcpStreamableHttp()` routes) — but that SDK is 0.13.0.

### Micronaut — 5.0.5 (July 2026)
- **Health:** 5.0.0 GA May 2026, **Java 25 baseline**, GraalVM 25; patches flowing (5.0.4 Jul 7, 5.0.5 Jul 16). Sources: [5.0.0 announcement](https://micronaut.io/2026/05/20/micronaut-framework-5-0-0-released/), [5.0.5](https://micronaut.io/2026/07/16/micronaut-framework-5-0-5-released/).
- Strengths: compile-time DI (no reflection → clean native images ~similar to Quarkus), Micronaut Security OIDC supports multiple providers via config, micronaut-openapi compile-time spec generation, micronaut-data-jdbc, Flyway. Kotlin supported (KSP).
- Risks: a **two-month-old major release** with a 70+ module platform refresh — early-adopter tax for a solo operator; community/mindshare smaller than Quarkus; MCP story = raw Java SDK, no framework extension found.

### Javalin — 7.2.2 (May 2026)
- 7.0 (Feb 2026) rebased on Jetty 12/Java 17/Kotlin 2; frequent releases. Sources: [Javalin 7 announcement](https://javalin.io/news/javalin-7.0.0-stable.html), [download](https://javalin.io/download).
- Tiny, unopinionated, superb for AI agents (small API surface). But: security = pac4j/DIY, OpenAPI via community `javalin-openapi` annotation processor, no native-image story to speak of, and MCP only via Java SDK servlet transport. Great micro-framework, weakest *secure-defaults* posture of the five.

### http4k — v6 line (last modules released 5 July 2026)
- Healthy, but note the **commercial split: Community Edition vs paid Enterprise Edition**, CE major cadence aligned to Jan 2027 — [v6/EE announcement](https://www.http4k.org/news/http4k-v6-and-ee/). Typesafe contract-first OpenAPI is genuinely excellent; functional style is polarizing for AI agents (less training-corpus convention); OIDC/authz largely DIY; GraalVM works (pure functions, no reflection). The EE licensing drift is a governance risk for a solo shop picking a 5-year foundation.

## 3. Go (chi/echo + pgx/sqlc)

- **Language:** Go 1.26 (Feb 2026) — Green Tea GC default, new `crypto/hpke`, `runtime/secret` (secure memory erasure), FIPS 140-3 mode. Sources: [go.dev/blog/go1.26](https://go.dev/blog/go1.26), [release notes](https://go.dev/doc/go1.26).
- **Security posture:** strong and arguably the most legible of any candidate: security fixes for the two most recent majors on a published policy; curated **Go vulnerability database + govulncheck** which reports only vulns in functions you actually *call*; module proxy + **checksum DB (sumdb)** gives tamper-evident supply chain by default; native fuzzing; FIPS mode. Source: [go.dev/security](https://go.dev/security/). A typical chi+pgx service has a dependency tree of a few dozen modules vs hundreds of jars — materially lower supply-chain surface. What Go does **not** give you: framework-level secure defaults — authz middleware, CSRF, OIDC multi-provider are assembled by you from small libs.
- **Ecosystem status (all verified maintained):** [coreos/go-oidc v3](https://github.com/coreos/go-oidc/releases) (release June 2026) for multi-provider OIDC (one verifier per issuer — simple loop); [sqlc 1.31.1](https://docs.sqlc.dev/en/stable/reference/changelog.html) (Apr 2026) + pgx/v5 — compile-time-typed SQL, superb for a rules-heavy relational domain and superb for AI agents (the SQL *is* the source of truth); [oapi-codegen v2](https://github.com/oapi-codegen/oapi-codegen) active (spec-first: you write OpenAPI YAML, generate server stubs + reuse same spec for TS types — actually the cleanest contract discipline of all options); migrations via goose/golang-migrate/atlas; **River** job queue (Postgres-native, type-safe generics, SOC 2 Type II as of Mar 2026, resumable jobs May 2026 — [riverqueue.com/blog](https://riverqueue.com/blog)) is an excellent fit for scheduled scans + LLM pipelines in the same Postgres.
- **MCP:** official SDK stable (see §1), trivially mounted on the same mux.
- **AI-assist:** arguably the best of all — explicit, boring, massive corpus, gofmt-uniform. Weakness for *this* domain: no sum types/sealed hierarchies/exhaustive matching — compliance rule engines are less pleasant to model than in Kotlin.

## 4. Quantitative: is "JVM too heavy for cheap PaaS" still true in 2026?

| Stack | Cold start | Idle RSS | Fits in |
|---|---|---|---|
| Ktor / JVM (JDK 21+, container-aware G1, AOT/CDS) | ~1–2 s (3–10 s worst-case container cold start) | ~150–300 MB | 512 MB–1 GB ✔ |
| Quarkus **native** | **20–80 ms** | **20–50 MB** | 128–256 MB ✔ |
| Quarkus JVM mode | ~1 s app start; 3–10 s container cold | 200–500 MB | 512 MB–1 GB ✔ |
| Go (chi + pgx) | ~10–50 ms | ~10–30 MB | 128 MB ✔ |

Sources: [oneuptime Cloud Run measurements, Feb 2026](https://oneuptime.com/blog/post/2026-02-17-quarkus-native-application-cloud-run-minimal-cold-start/view) (Quarkus native 20–80 ms / 128Mi vs JVM 200–500 MB); [GraalVM native-image guide](https://oneuptime.com/blog/post/2026-02-20-java-graalvm-native-image/view); comparative 2026 shootouts report Quarkus native ~70 MB total RSS ([javacodegeeks 2026 comparison](https://www.javacodegeeks.com/2025/12/spring-boot-vs-quarkus-vs-micronaut-the-ultimate-2026-showdown.html)).

**Verdict:** the claim is obsolete *if* you use native image (Quarkus/Micronaut) — Java then matches Go's scale-to-zero economics. It remains *half-true* for plain-JVM Ktor/Javalin: you'll want a 512 MB–1 GB always-on instance (`min-instances=1`). At 60 users that's roughly $10–25/month on Cloud Run — a real but small tax; CRaC does not rescue this on Cloud Run (no checkpoint/restore support in the platform).

## 5. Ranked Recommendation

### #1 — Quarkus 3.33 LTS with Kotlin
Wins on the weighted criteria: **security defaults** (only candidate with config-level multi-provider OIDC federation, declarative authz, curated BOM, Red Hat-backed LTS patch stream), **MCP** (the most mature MCP server implementation on any JVM — annotation-driven, CDI-injected into your service layer, already on the 2026-07-28 stateless protocol), **footprint** (native image = Go-class economics), **solo-operability** (batteries included: Flyway, scheduler, OpenAPI, health, metrics — one coherent, heavily documented platform, none of it Spring), **AI-assist** (huge conventional guide corpus). Kotlin is officially first-class even if examples skew Java.

**2–3 day spike must validate:**
1. Kotlin + `quarkus-rest` + `quarkus-mcp-server-http` in one app, MCP tool calling the same CDI service as a REST endpoint; confirm streamable HTTP with a real MCP client (Claude Code).
2. OIDC multitenancy with two live providers (Entra + Google) incl. `TenantResolver` and `@PermissionsAllowed`-style row-level check.
3. **Native image build of exactly that combo** (MCP ext + OIDC + Hibernate/jOOQ + Flyway + JobRunr): does it compile and run in 256 MB? If native fights you, confirm JVM-mode fallback fits your PaaS budget.
4. SmallRye OpenAPI output → openapi-generator TS types round-trip.
5. How Claude Code copes with Kotlin-flavored Quarkus (translate a Java guide sample; assess friction).

### #2 — Go 1.26 (chi + pgx/sqlc + oapi-codegen + river + go-oidc)
Wins on **runtime footprint, supply-chain minimalism, deployment simplicity (one static binary), stable official MCP SDK, and AI-assist**. The security *story* is verifiably strong (govulncheck/sumdb/FIPS/policy). Costs: abandons JVM proficiency; secure defaults are assembled, not inherited; weaker domain-modeling ergonomics for a rules engine; OIDC/CSRF/authz all explicit code you must get right once.

**2–3 day spike must validate:**
1. Official go-sdk `StreamableHTTPHandler` mounted beside oapi-codegen-generated chi routes, sharing one service struct; test with Claude Code. Decide v1.6.1 vs waiting for v1.7.0 (2026-07-28 protocol).
2. go-oidc against Entra + Google + Okta (issuer-per-tenant verifier map); token → row-level authz middleware.
3. sqlc modeling of a representative compliance rule query set — does the rules engine feel tolerable without sum types?
4. River for a scheduled scan + a multi-step LLM extraction job (resumable jobs feature).
5. `govulncheck` in CI + distroless image; measure real idle RSS/cold start on Cloud Run.

**Why not the others, in one line each:** **Ktor** — lovely Kotlin DX, but pre-1.0 MCP SDK on a day-one hard requirement, experimental OpenAPI gen, and DIY security posture make it a build-your-own-Quarkus exercise; reconsider if MCP Kotlin SDK hits 1.0 before you start. **Micronaut 5** — technically strong but a 2-month-old major platform with no MCP extension is the wrong early-adopter bet for a solo team. **Javalin/http4k** — maximal simplicity but minimal secure defaults, and (http4k) EE commercial-split governance risk.
