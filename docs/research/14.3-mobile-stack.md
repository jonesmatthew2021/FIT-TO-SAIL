# §14.3 Mobile stack — research report

**Research date:** 26 July 2026 (live web verification). Where a claim rests on a single secondary source (e.g. Medium posts), it is flagged as lower-confidence.

## 1. Flutter

### Version & health
- **Current stable: Flutter 3.44** (3.44.0 released 18 May 2026; patch releases up to 3.44.7 as of late July). Cadence steady through 2026. ([Flutter SDK archive](https://docs.flutter.dev/install/archive), [What's new in Flutter 3.41](https://blog.flutter.dev/whats-new-in-flutter-3-41-302ec140e632))
- **Google investment signal: "steady, not growing."** The April 2024 layoffs remain the defining data point, but two-year retrospectives (April 2026) note the project kept shipping its roadmap: Impeller stable, Dart 3.x, releases on schedule. Google publicly reaffirmed Flutter as strategic (Google Earth, Classroom run on it; ~1M+ apps in stores). Honest read: **no evidence of abandonment, but also no evidence of expanded investment** — a maintenance-plus posture. ([TechCrunch](https://techcrunch.com/2024/05/01/google-lays-off-staff-from-flutter-dart-python-weeks-before-its-developer-conference/), [The New Stack](https://thenewstack.io/whats-next-for-flutter-after-layoffs-hit-google-team/))

### Offline DB (drift + encryption)
- **Important 2025/26 change:** as of **drift 2.32.0 + sqlite3 package 3.x**, the officially recommended encrypted path is **`NativeDatabase` + SQLite3MultipleCiphers** (enabled via a pubspec build hook, `sqlite3: source: sqlite3mc`), *not* SQLCipher. The old `sqlcipher_flutter_libs` route is effectively deprecated for new setups. Works on Android, iOS, macOS, desktop. Drift docs explicitly recommend runtime verification that the cipher pragma is active. ([drift encryption docs](https://drift.simonbinder.eu/platforms/encryption/))
- Spec implication: replace "drift + SQLCipher" with **"drift + SQLite3MultipleCiphers"** — same AES-256 at-rest guarantee, simpler build, actively supported. Key material in Keychain/Keystore via flutter_secure_storage.

### Camera / document capture
- **`google_mlkit_document_scanner`**: full scan UI with edge detection, auto-crop, multi-page — but **Android-only**. ([pub.dev](https://pub.dev/packages/google_mlkit_document_scanner))
- Cross-platform options wrap **ML Kit (Android) + VisionKit (iOS)** behind one Dart API: `flutter_doc_scanner`, `doc_scanner_kit`. Commercial fallback: Scanbot SDK. ([Flutter Gems doc-scanner index](https://fluttergems.dev/document-scanner/))
- Net: requirement met, via community wrappers around two different OS scanners — pin versions and test both platforms (this is where parity needs watching).

### Background upload
- **`background_downloader`** (actively maintained; does uploads too): URLSession on iOS / WorkManager on Android, survives app kill, retries, **resumable/chunked upload** support. Alternatives: `flutter_uploader` (older, slower-moving), `native_workmanager` (chunked/resumable HTTP workers), tus-style `resumable_upload`. ([background_downloader](https://pub.dev/packages/background_downloader))
- **Strong** story for the maritime-connectivity requirement: OS-level background sessions on both platforms plus app-level resumability.

### Push, OIDC, secure storage
- Push: `firebase_messaging` (FCM both platforms; APNs via FCM). Standard.
- OIDC: **`flutter_appauth`** wraps AppAuth-iOS/Android; auth-code+PKCE; actively maintained. ([pub.dev](https://pub.dev/packages/flutter_appauth))
- Secure storage: **`flutter_secure_storage` v10** (2026) — Keychain / Keystore-backed AES-GCM, biometric-bound storage; pair with `local_auth`. Note: biometric *prompt* ≠ biometric-*bound key* — for the DB-key unlock you want the latter (Keystore key tied to biometric enrollment). ([flutter_secure_storage](https://github.com/juliansteenbakker/flutter_secure_storage))

### AI-assist affinity
- Multiple 2026 sources report Flutter as highly agent-friendly: Dart's strong typing + rigid project structure reduce hallucination. Counterpoint: npm/TS has far more training data. Practical consensus in 2026: **both are well within "AI agents work great" territory**; Dart's analyzer + strict types give tighter feedback loops. (Secondary sources, lower confidence.)

## 2. React Native + Expo

### Version & architecture
- **Expo SDK 57** (30 June 2026) ships **React Native 0.86**; "small, focused release", no breaking changes from 0.85. ([Expo SDK 57 changelog](https://expo.dev/changelog/sdk-57))
- **New Architecture transition finished**: Legacy Architecture removed at RN 0.83 / Expo SDK 55; New Architecture always-on. ~85% of popular packages compatible. Multi-year migration churn now behind the ecosystem. ([Expo new-architecture guide](https://docs.expo.dev/guides/new-architecture/))

### EAS Build / Update & App Store policy
- EAS Build/Submit is the best solo-dev release pipeline of the three stacks (cloud builds, managed signing, store submission).
- **EAS Update (OTA)** is compliant with Apple DPLA §3.3.1(B): JS/asset changes only. For a compliance product, OTA is a nice-to-have and extra security surface to govern. ([Expo EAS Update docs](https://docs.expo.dev/eas-update/introduction/))

### SQLite / encryption
- **`expo-sqlite` supports SQLCipher natively** (`useSQLCipher` in app config + prebuild; needs dev build, which CREWCOMP would use anyway). ([Expo SQLite docs](https://docs.expo.dev/versions/latest/sdk/sqlite/))
- **`@op-engineering/op-sqlite` + SQLCipher** is the high-performance option (PowerSync funded SQLCipher support).
- Key storage: `expo-secure-store` + `expo-local-authentication`. Solid.

### Camera / document scan
- **`react-native-document-scanner-plugin`** (VisionKit iOS / ML Kit Android, multi-page); newer **`@dariyd/react-native-document-scanner`** is New-Arch-native. Commercial: Scanbot, Dynamsoft. Same underlying OS scanners as Flutter — equivalent capability and parity caveat.

### Background upload / queue durability — the weak spot
- **RN's weakest area for CREWCOMP's hardest requirement.** `expo-background-task` schedules OS-fired work (~15-min minimum windows, opportunistic) — fine for sync ticks, not a true background transfer API. The once-standard `react-native-background-upload` (Vydia) is effectively unmaintained. Durable chunked/resumable upload surviving app kill generally means hand-rolling over `expo-task-manager` + `expo-file-system`, or writing a native module around NSURLSession background sessions / WorkManager — i.e. the thing Flutter's `background_downloader` already packages.

### OIDC
- **`react-native-app-auth`** remains the standard; its repo carries a maintenance-status caveat and stewardship has been shakier than flutter_appauth's — verify maintainer activity before committing. `expo-auth-session` is the JS-level PKCE alternative.

### Supply-chain posture (decisive for "security paramount")
- npm has had a brutal 12 months: **Shai-Hulud** (Sept 2025, first self-propagating npm worm), **Shai-Hulud V2** (Nov 2025: 700+ packages, ~27k malicious repos, ~14k secrets across 487 orgs within hours), **Mini Shai-Hulud** (May 2026: 170+ npm + PyPI packages targeting CI/CD credentials). CISA issued ecosystem-wide alerts. ([Wiz](https://www.wiz.io/blog/shai-hulud-npm-supply-chain-attack), [Microsoft](https://www.microsoft.com/en-us/security/blog/2025/12/09/shai-hulud-2-0-guidance-for-detecting-investigating-and-defending-against-the-supply-chain-attack/), [CISA](https://www.cisa.gov/news-events/alerts/2025/09/23/widespread-supply-chain-compromise-impacting-npm-ecosystem))
- Mitigable (lockfiles, `--ignore-scripts`, version cooldowns, minimal dep tree, provenance) but a typical RN/Expo app pulls **hundreds of transitive npm packages** vs a much smaller pub.dev tree (no install scripts by default). A real, ongoing operational tax on RN for a compliance product, not a disqualifier.

## 3. Kotlin Multiplatform + Compose Multiplatform

### iOS maturity (July 2026)
- **CMP for iOS officially Stable since 1.8.0 (May 2025).** Since then: **1.10.0 (Jan 2026)** — unified `@Preview`, Navigation 3, stable Compose Hot Reload; **1.11.0 (May 2026)** — concurrent rendering on by default on iOS, Compose UI testing v2 on non-Android targets, *experimental* native iOS text input. ([JetBrains 1.8.0](https://blog.jetbrains.com/kotlin/2025/05/compose-multiplatform-1-8-0-released-compose-multiplatform-for-ios-is-stable-and-production-ready/), [1.10.0](https://blog.jetbrains.com/kotlin/2026/01/compose-multiplatform-1-10-0/), [1.11.0](https://blog.jetbrains.com/kotlin/2026/05/compose-multiplatform-1-11-0/))
- Honest read: rendering/performance genuinely production-grade; full-CMP-UI iOS apps are newer and fewer. **Native text input only arriving as experimental in May 2026** shows where the polish frontier is — exactly the last-5% detail a solo dev has no bandwidth to fight.

### Data & networking
- **SQLDelight 2.x** actively maintained; Room gained KMP support. **Encryption on iOS is more manual** — you wire SQLCipher into the native driver per platform yourself. **Ktor 3.x** client pairs beautifully with a Kotlin backend (shared DTOs, kotlinx.serialization end-to-end).

### Camera, push, biometrics — still per-platform
- Push: **KMPNotifier** wraps FCM/APNs acceptably. **No mature KMP wrapper for VisionKit + ML Kit doc scanning exists** — you write the Swift and Kotlin integrations yourself behind expect/actual. Same for background NSURLSession upload sessions.

### Realistic extra effort for CREWCOMP
CREWCOMP's feature set is **unusually native-API-heavy** (doc-scan camera UI, background transfer, biometric-bound keys, push). With KMP each is Swift + Kotlin written twice by hand; with Flutter/RN each is an existing maintained package. Estimate **+30–50% effort vs Flutter for this specific app**, plus genuine Swift/Xcode proficiency to acquire. One-language-with-backend pays off most in logic-heavy apps — this app's risk is concentrated in exactly the platform-glue layer KMP doesn't abstract.

## 4. Cross-cutting comparison

| Dimension | Flutter | RN + Expo | KMP + CMP |
|---|---|---|---|
| **Parity risk** | Lowest — one renderer, one codebase; only the doc-scanner diverges | Low-moderate | Every hand-written expect/actual native module is a parity bug farm |
| **Solo-dev testing** | Best: widget/golden/integration tests, one suite | Good: Jest + RNTL, Maestro/Detox | Shared-logic tests excellent; CMP UI testing v2 only landed May 2026 |
| **Release automation** | Codemagic or fastlane + GH Actions; good | **EAS Build/Submit — best in class** | Most manual (Gradle + Xcode dual build) |
| **Upgrade churn** | Moderate; historically smooth | Historically worst, but New-Arch migration done; improving | Kotlin/Gradle/AGP/Xcode version matrix is the real churn |
| **Supply chain** | pub.dev, no install scripts, small trees — low | **npm — demonstrably the highest-risk ecosystem 2025–26** | Maven Central/CocoaPods — lowest |
| **Ecosystem risk** | Google steady-not-growing | Meta + Expo heavily invested; healthiest momentum | JetBrains committed; smallest mobile-feature ecosystem |
| **Language sharing** | None (Dart island) | TS shared with React admin app | Kotlin shared with Kotlin backend |

**Sync-layer sanity check (hand-rolled vs PowerSync/ElectricSQL/WatermelonDB):** The "just use PowerSync" consensus targets apps with bidirectional multi-writer sync and conflict resolution. CREWCOMP is not that: reads are server-authoritative read-only lists (snapshot + delta), writes are an **append-only outbound submission queue** — essentially no conflict domain. PowerSync would add a sync service + Postgres logical-replication infrastructure and a vendor dependency to a 60-user app. **The spec's preference for a thin hand-rolled sync client over encrypted SQLite is sound** — design the delta contract carefully (server-issued cursors, idempotent upserts, tombstones) and revisit if crew-editable shared records ever appear.

## 5. Ranked recommendation

### #1 — Flutter (recommended)
- **Hard parity + solo dev:** one codebase, one renderer, one test suite — parity is structural, not disciplined-for. Only per-platform seam is the document scanner, already bridged by packages.
- **The hard 20% (offline/camera/upload) is all packaged:** drift + SQLite3MultipleCiphers, `background_downloader` (kill-surviving, resumable), doc-scan wrappers, `flutter_appauth`, `flutter_secure_storage` v10 + `local_auth` with biometric-bound keys. Nothing on the feature list requires writing native code.
- **Security posture:** pub.dev's small, script-free dependency trees are materially lower supply-chain exposure than npm.
- **Accepted risks:** Google's steady-not-growing investment (mitigated by ~1M-app installed base); Dart shares no code with backend or admin app (mitigated: thin REST contract, OpenAPI-generated on both sides).

### #2 — React Native + Expo
- Strongest release automation (EAS), New-Arch churn over, first-class SQLCipher, TS shared with admin app, biggest AI corpus.
- Second on two CREWCOMP-specific grounds: **(a)** durable chunked background upload — the single hardest feature — has no maintained off-the-shelf answer; **(b)** npm supply-chain risk is a permanent operational tax on a compliance product.

### Why KMP is third despite the Kotlin backend
This app's risk is concentrated in platform glue — precisely what KMP makes you build twice by hand, in Swift the developer doesn't yet write, with the smallest package ecosystem and newest UI-testing story. For a logic-heavy app KMP would rank second; for *this* feature set it is the highest-effort, highest-parity-risk shared option for a solo dev. Keep as fallback if a spike reveals Flutter dealbreakers.

### 1-week comparative spike (Flutter vs RN/Expo, same slice in both)
Build the riskiest vertical slice, not the CRUD:
1. **Day 1–2 — encrypted store + sync:** encrypted SQLite, key in Keychain/Keystore behind biometric-bound unlock; snapshot + delta pull against a stub REST server; kill the app mid-sync and verify recovery.
2. **Day 3–4 — the upload gauntlet:** queue a 20 MB multi-page submission; toggle airplane mode mid-chunk, force-kill, background 30 min — verify resume-from-offset, backoff, server-side reassembly (tus or custom Content-Range).
3. **Day 5 — capture + auth:** 3-page scan with edge guidance on physical iPhone + Android; OIDC auth-code+PKCE against a real corporate IdP test tenant with refresh rotation.
4. **Scorecard:** lines of per-platform/native code, hours lost to toolchain, package health of every dependency touched, subjective Claude Code friction. The upload gauntlet is the expected decider — if RN needs a custom native module there, Flutter wins outright.
