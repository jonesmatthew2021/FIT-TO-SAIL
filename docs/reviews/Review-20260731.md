# End-user review — 31 July 2026

A functionality, logic and layout review of the whole product as an end user meets it:
the admin console's eleven modules, the crew app's twelve screens, and the engine
semantics underneath, reviewed against the spec and driven through the source. The
review also catalogued automation opportunities, one of which — auto-suggesting an
entire swing roster — was specced in full as
[`docs/spec/roster-assist-spec.md`](../spec/roster-assist-spec.md) and is tracked in
[#22](https://github.com/cdjones32/attest/issues/22).

Everything actionable below was filed on 31 Jul 2026 as GitHub issues
[#9–#23](https://github.com/cdjones32/attest/issues). Each entry links to its issue;
items inside the two batch issues link to [#20](https://github.com/cdjones32/attest/issues/20)
(admin) or [#21](https://github.com/cdjones32/attest/issues/21) (mobile), where they are
tick-boxes. Items marked *not filed* are observations or larger directions that were
deliberately left out of the tracker.

## Overall verdict

Per screen this is an unusually well-reasoned product: honest empty states, a refusal to
fake compliance answers, server-owned semantics, the 409-as-question flows, the crew
app's five-state answer model, and an exemplary privacy posture on the supervisor's team
view. The weaknesses are consistently **at the seams** — between screens (no bulk
actions, broken deep links, queues without queue affordances), between client and server
(client-derived readiness contradicting the engine), and between components (config
that is settable but never read).

## 3. Logic and copy risks — deliberate design attention needed

Mostly not filed as defects: these are places where correct semantics will read as bugs
to end users unless the screens say more.

- **`pending` outranks `unknown`, and `exempt` is not `ok`** — raising paperwork changes
  a person's headline state though nothing about their certificates changed. The admin
  dashboard's "All clear" can conceal pending/exempt cells. *Not filed; partly covered
  by [#12](https://github.com/cdjones32/attest/issues/12)'s server-side headline.*
- **Two people see deliberately different urgency for the same certificate** — "course
  booked" silences the crew member's warning (`ON_WORD`) but never the coordinator's;
  a seat request suppresses nothing (`ON_ACTION`) and the app never says so, so crew
  will keep receiving alerts after "handling it". Suppression resuming automatically
  when an expiry moves is equally invisible. *Not filed: needs a copy pass, flagged in
  [#16](https://github.com/cdjones32/attest/issues/16) and
  [#23](https://github.com/cdjones32/attest/issues/23).*
- **"Fully crewed" can hide holes** — the planner headline counts open slots only; a
  swing with a three-day gap in every slot reads "fully crewed" with `Part-covered: 12`
  in a plain tile (`SwingPlanner.tsx:174`). *Not filed.*
- **The declaration wording is a client constant** — what a crew member signed depends
  on which app build they had; the server stores ids, not sentences. Should come down
  the wire (handoff §2.5/§6). *Not filed; known handoff item.*
- **Raw vocabulary leaks on the crew phone** — `M`/`R`/`M9` levels, `MS`/`QL` category
  codes, wire-format reason labels (`no_seat`, `with_authority`), with no glossary
  anywhere in the app. *Covered by [#23](https://github.com/cdjones32/attest/issues/23).*
- **Admin instant timestamps are browser-local beside AWST business dates**
  (notifications, evidence, job runs). *Covered by
  [#23](https://github.com/cdjones32/attest/issues/23).*
- **The one-tap timeline promises an "In progress" state no screen ever shows**
  (`action_screens.dart` WHAT HAPPENS steps) — the promise is unverifiable from the
  crew member's side. *Not filed.*
- **The exemption flow's before/after contradiction** — "you cannot sail past 14 Aug"
  → send → "You can sail this swing." *Covered by
  [#12](https://github.com/cdjones32/attest/issues/12).*
- **"Nothing is recorded against you for asking for help"** is a promise about
  consequence, not storage — a row is created; the engine never reads it. Worth a wording
  check before a privacy review reads it the stronger way (handoff flags this too).
  *Not filed.*
- **MOB-8's "The company pays"** is an unqualified financial promise rendered from a
  client constant, on any requirement, with no policy source. *Not filed — needs a
  client decision, not code.*
- **ISO dates still leak into crew-facing notification bodies**; the mobile client
  rewrites them at display time, the admin centre shows them raw. Fix at composition
  (handoff §8). *Not filed; known handoff item.*

## 4. Layout and consistency — covered by [#23](https://github.com/cdjones32/attest/issues/23)

- **No bulk actions anywhere in the admin app.** Chasing 14 unknown holdings is 14
  person-page round trips; moving 8 register records is ~32 interactions; a 40-cell
  matrix column edit is 40 PUTs and full refetches; ADM-9's spot-check stage is
  one-at-a-time sampling.
- **Selection state is held four different ways** (route / URL query / component state /
  modal) so only some views are shareable; ADM-3's generated-per-swing choice is lost on
  tab switch.
- **Five segmented-control vocabularies** for "which subset", plus ADM-9's checkboxes;
  filter controls live in two different homes; `errorText()` is copy-pasted into six
  screens.
- **Queues without queue affordances**: no badges for crew requests, evidence depth or
  exceptions; nothing cross-links a queue item to the swing it blocks ("this document
  blocks UNI CC24 in 4 days").
- **The mirrored 90-day constant**: the dashboard lead-time default and ADM-5's expiry
  colour bands use a client constant, not the live `expiry.lead-days` setting — the same
  class of issue as the mobile app's mirrored `90`.
- **Suggestion weights are edited as raw JSON in a single-line input** — the screen that
  decides who the planner recommends is the least legible in the app.
- **No audit log view** — six places say "this is audited"; nothing lets an operator
  read it, though events already carry `businessKey`, `before`, `after`,
  `clashAcknowledged`.
- **Mobile has no settings/profile surface**: no sign-out or "this is not me", no
  support contact, no app version, no glossary, no manual clear-and-resync.
- Sticky headers only on the matrix grid; screen widths vary without a stated rule;
  the ruler's bars are `aria-hidden` with dates only in a `data-dates` attribute
  (screen-reader users on wide viewports lose the windows); `ADM-n` codes ship in the
  production nav.

### 5.4 Deliberately not automated

Anything that re-derives compliance client-side (AUTH-1), assistant writes (LLM-1),
auto-approving register records (Q14 — the Workflow Manager is sole decision authority),
auto-closing crew requests (a statement is not a compliance answer), correcting the
extraction record itself (it is the accuracy measurement LLM-2 needs), and — per the
Roster Assist spec §8 — auto-applying a roster at any threshold, in any phase.

## Method

Four parallel research passes over the source and spec (domain semantics; admin-web
end-user walkthrough; mobile end-user walkthrough; backend engine and planner data
audit), synthesised on 31 Jul 2026 against commit 382e3f2. File:line references are to
that commit. No screens were driven live during this review; findings are code-derived
and the highest-risk ones should be confirmed on a simulator/browser when fixed.
